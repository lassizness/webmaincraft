# HiveTech Telemetry API v1

Server-to-server API for the future `HiveTechTelemetry` Forge mod.

The API intentionally reuses the existing per-server Bridge credential.
The token is the same `htb_...` token issued on the server Bridge page.
The telemetry mod must never log or expose that token.

## Authentication

Every request requires:

```http
Authorization: Bearer htb_<token>
X-HiveTech-Server: <server-code>
Content-Type: application/json
```

Base URL:

```text
/internal/game
```

Example production base:

```text
https://hivegrid.online/internal/game
```

## POST /telemetry/events

Accepts a batch of 1 to 500 events.

Maximum request body: 2 MiB.

Every event has its own UUID. The backend stores `event_uuid` under a
unique index and uses `INSERT IGNORE`, therefore retrying an already
accepted batch is safe and does not increment counters twice.

Request:

```json
{
  "events": [
    {
      "id": "5e733d4e-575e-4aa6-bdfb-ef7587419341",
      "session_id": "c3693a87-75ad-49f0-89cc-52d262766add",
      "player_uuid": "c97ef9dd-ec55-4fc9-8284-618dc9a88baa",
      "username": "Player",
      "type": "block.break",
      "source": "forge",
      "object": "minecraft:diamond_ore",
      "amount": 3,
      "occurred_at": "2026-10-09T17:30:00+05:00",
      "metadata": {
        "dimension": 0
      }
    }
  ]
}
```

Fields:

- `id`: required UUID, stable across retries.
- `session_id`: optional UUID generated by the telemetry mod for one player connection.
- `player_uuid`: optional Minecraft UUID.
- `username`: optional Minecraft username.
- `type`: required lower-case event key, max 64 chars.
- `source`: optional source key, defaults to `forge`.
- `object`: optional registry/object id, max 128 chars.
- `amount`: positive integer, defaults to 1.
- `occurred_at`: ISO-8601 string, Unix seconds or Unix milliseconds. If omitted, backend receive time is used.
- `metadata`: optional JSON object, max 8 KiB after encoding.

The backend resolves a portal user by username first and then by portal UUID.
This is intentional because the portal UUID can differ from the runtime
Minecraft UUID depending on the launcher/auth stack.

Unresolved player events are preserved as raw telemetry but do not modify
player counters or achievements.

Response:

```json
{
  "api_version": 1,
  "server": {
    "id": 1,
    "code": "HiveTech"
  },
  "generated_at": "2026-10-09T12:30:01+00:00",
  "accepted": 1,
  "duplicates": 0,
  "unresolved_players": 0,
  "received": 1,
  "achievements_unlocked": []
}
```

If the same event is retried:

```json
{
  "accepted": 0,
  "duplicates": 1,
  "unresolved_players": 0,
  "received": 1,
  "achievements_unlocked": []
}
```

The full batch is validated before processing. A malformed event returns
HTTP 400 and the mod should not silently discard the batch.

## Event naming

Core Forge events:

```text
player.login
player.logout
player.playtime
player.death

block.break
block.place

item.craft
item.smelt
item.pickup

entity.kill
dimension.enter
advancement.complete
```

Compatibility adapters should use their own source and namespaced event keys.

Examples:

```text
source=ic2
ic2.machine.place
ic2.machine.craft
ic2.energy.tier_reached

source=ae2
ae2.network.created
ae2.autocraft.start
ae2.autocraft.complete
ae2.storage.cell_created

source=thermal
thermal.machine.place
thermal.augment.install

source=forestry
forestry.bee.discovered
forestry.bee.mutation
forestry.apiary.place
```

The generic Forge layer must still emit normal item/block registry IDs for
IC2, AE2, Thermal and Forestry even when a compatibility adapter is not
available.

## Aggregated stat keys

For every normal event the backend increments:

```text
<event-type>.total
```

When an object exists it also increments:

```text
<event-type>.<object>
```

Examples:

```text
item.craft.total
item.craft.appliedenergistics2:controller

entity.kill.total
entity.kill.minecraft:zombie

ic2.machine.place.total
ic2.machine.place.ic2:te
```

Compatibility aliases:

```text
block.break  -> blocks.break.total
block.place  -> blocks.place.total
player.playtime -> playtime_seconds
```

`dimension.enter` is additionally deduplicated in
`player_discoveries`, producing:

```text
dimensions.visited
```

Any event ending in `.discovered` is also stored as a unique discovery and
increments:

```text
<event-type>.unique
```

Example:

```text
forestry.bee.discovered.unique
```

## Sessions

The mod should generate a new `session_id` when a player joins and include it
on all events for that connection.

`player.login` opens the session. Any event updates `last_event_at`.
`player.logout` closes it.

A maintenance job closes stale sessions after five minutes so a server crash
does not leave players online forever.

Recommended playtime event:

```json
{
  "type": "player.playtime",
  "amount": 60
}
```

Send it approximately once per minute for every online player.

## Achievement evaluator

After a batch updates player stats the backend recalculates enabled
achievements for the affected users.

Conditions in the same `group_no` use AND.

Different groups use OR.

Therefore:

```text
group 1: A + B
group 2: C + D
```

means:

```text
(A AND B) OR (C AND D)
```

When an achievement is completed the backend inserts one idempotent
`achievement_unlocks` row and returns it in `achievements_unlocked`.

Achievement rewards are marked `pending` when configured. Reward execution
is deliberately separate from event ingestion so a failed external reward
cannot cause an accepted telemetry batch to be replayed.

The reward worker is:

```text
php yii achievement/process-rewards 50
```

Supported reward payloads:

```json
{"amount":500}
```

for `wallet`;

```json
{"server_id":1,"command":"give {username} minecraft:diamond 1"}
```

for `rcon`;

```json
{"name":"launchserver.permission.example"}
```

for `permission`;

```json
{"server_id":1,"group_id":2,"days":30}
```

for `privilege`.

Each unlock/reward pair has a unique delivery record. Wallet, permission,
privilege and RCON-queue writes happen inside a database transaction before
the delivery is marked done. Failed rewards retry with backoff up to five
attempts.

## POST /telemetry/heartbeat

Recommended cadence: every 60 seconds.

Request:

```json
{
  "telemetry_version": "1.0.0",
  "minecraft_version": "1.12.2",
  "forge_version": "14.23.5.2860",
  "online_players": 12,
  "queue_size": 0,
  "buffered_events": 3,
  "last_error": ""
}
```

Response:

```json
{
  "api_version": 1,
  "server": {
    "id": 1,
    "code": "HiveTech"
  },
  "generated_at": "2026-10-09T12:31:00+00:00",
  "accepted": true,
  "max_batch_size": 500,
  "server_time": "2026-10-09T12:31:00+00:00"
}
```

The admin dashboard considers telemetry online when the last heartbeat is
not older than 120 seconds.

## Client queue behaviour

The mod should:

1. Persist its queue to disk.
2. Never perform HTTP from the Minecraft server thread.
3. Aggregate high-frequency counters before enqueueing them.
4. Send batches every 3-10 seconds or when the queue reaches a threshold.
5. Keep the same event UUID across retries.
6. Delete local events only after a successful API response.
7. Apply exponential retry/backoff on network and 5xx failures.
8. Preserve events across Minecraft restarts.
9. Send heartbeat every 60 seconds.
10. Never log the bearer token.

Unknown player events are not a reason to retry forever: the API can accept
them and report them through `unresolved_players`.

## Retention

Raw `telemetry_events` are retained for 30 days by default.

The following are not deleted by raw-event retention:

- `player_stats`
- `player_discoveries`
- `player_sessions`
- achievement progress
- achievement unlock history
